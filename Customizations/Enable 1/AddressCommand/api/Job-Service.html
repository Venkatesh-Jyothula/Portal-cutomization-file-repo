Job Service

Job Service API Overview

The HxGN NetWorks Job Service provides methods that allow clients to use HxGN NetWorks Core jobs in their viewing and editing workflows, and to manage jobs. The get jobs by filter, get picklist values and get pending edits workflows require the Networks_UseJobs license feature. All other job service workflows require the Networks_ManageJobs license feature.

Supported Job Workflows

Create a new job

Call the /create/{jobId?} method to create a new HxGN NetWorks Core job. If the job identifier is included in the call, it must be unique among all jobs. If no job identifier is sent to the method, then a new job identifier is generated by concatenating the G3E_JOBDEFINITION.G3E_JOBPREFIX value and the next sequence value from the G3E_JOB_SEQ sequence that is unique.

The JSON response always includes the new job's core properties: identifier, description, owner, and status. The identifier property is the job Id that was passed in or the generated job Id. Description is initially an empty string value; owner is the Oracle user from the request's database connection; and the status property will be set to "Open". When the optional jobDialogType query string parameter is specified, then all of the attributes associated with the specified dialog are appended to the response as a properties collection.

Close an existing job

Call the /close/{jobId} method to close an existing HxGN NetWorks Core job that is no longer needed. The job cannot be closed if there is another user is actively using the job. Also, any pending edits must be either posted or discarded before the job can be closed.

The JSON response always includes the same core properties, identifier, description, owner, and status, that create job returned except that the status value will be set to "Closed". When the optional jobDialogType query string parameter is specified, then all of the attributes associated with the specified dialog are appended to the response as a properties collection.

Edit a job's properties

Call the /edit method to post updates to a job's properties. Only the Description value and those properties that are marked, "IsReadonly": false, can be edited.

The methods that create jobs, close jobs and get jobs all take a query string parameter that specifies a jobDialogType that describes how to present the job's properties. Clients can take this JSON response, edit the values of the non-readonly properties, and POST the edited payload back to the /edit method. The new job properties response is returned based on the jobDialogType of the /edit request.

Get picklist values for a job property

Call the /picklistvalues/{ano} method to retrieve the key value pairs of possible property values for the specified job attribute number {ano}. In the job properties response from create, close, edit and jobs methods, a job property with IsPicklist set to true has a picklist that can be retrieve by using the job property's Ano field.

If the client is going to display the job's properties to the user, then this API supplies the picklist values to display to the user for a specific picklist key. In the display and edit job properties workflow, the picklist values are usually displayed in a drop down combobox that the user selects from.

Get a filtered list of jobs to work with

Call the /jobs method with one or more filters to get a list of jobs. Any combination of the filter parameters, which are based on the job's core properties (e.g. id, owner, status and description), can be specified. Requests must include at least one filter. The filter parameter values are used in a wild card match to the values in the corresponding columns in the job table. Multiple filters are AND'ed together in the query for jobs.

Clients call the /jobs method to retrieve information about jobs to present to the users. Most NetWorks Services APIs accept either a Jobs= query parameter, or an ActiveJob=<active job> to do edits in. The amount of job information returned is controlled by the jobDialogType query string parameter. Since the number of jobs that match the filter criteria can be large, the method supports pagination of the results via the pageNo and pageSize query string parameters.

List the pending edits in a job

Call the /pendingedits/{jobId} method to get the complete list of edits within the job. Each pending edit in the response contains the feature name, feature keys, and LTT_STATUS (such as Add, Delete, or Edit.)

Clients can use the jobId and feature keys in a subsequent call to the WMS GetGeometry method to get the GeoJson geometry that can be used to do a client side highlight on the map, or just fitting the map to the edited feature.

Discard pending edits in a job

Call the /discard method to remove all pending edits within a job. Alternatively, the client can call the /discardbyfid method with a POST body containing a JSON array of Fids to discard specific feature edits.

List pending edits that have conflicts

Call the /conflicts method to determine if any of the pending edits in the job have conflicts with the master version of the same features in the database. A conflict occurs when a feature that has been edited in the current job is also edited by another job that posts its edits first. A job with conflicts cannot be posted.

The /conflicts method returns a JSON array of conflicts. Each conflict contains the jobId, feature name, feature keys, LTT_STATUS and the database table that has the conflicting value. There is no further Job Service API for resolving conflicts. Conflict resolution can be done using the G/Designer desktop.

Validate the pending edits in a job

Call /validate/{jobId} to check whether the pending edits in the job conform to all of the HxGN NetWorks Core business rules for the structure of the features, components, attributes and relationships; and the custom rules in the Validate methods of the associated functional interfaces.

The response is a JSON array of validation errors where each error contains the feature keys, error priority, error description and error location information. The error priority values are P1, P2, P3 and P4 where P1 is the most severe. Only the validation errors whose error priority is higher than the ValidationPriorityFilter value from the G3E_GENERALPARAMETER table will be included in the response. A job cannot be posted if there are any validation errors that are higher than or equal to the ValidationPriorityThreshold value from the G3E_GENERALPARAMETER table.

Post pending edits

Call /post/{jobId} to post all pending edits within the specified job. The edited features will be checked to make sure that all required components, attributes and relationships have been created. Also, the Validate method of all associated Functional interfaces will be executed. If there are no validation errors at or above the metadata configured validation priority, then the job's feature edits will be checked for conflicts with master records of the same features that were posted by other jobs. If there are no job conflicts, then the feature edits are posted in the database as the new master version of the feature.

Transition Job and / or Feature State

HxGN NetWorks Core allows its customers to specify a column on a common component to hold the "state" of the feature. (See G3E_WORKMGMT_OPTABLE where G3E_TYPE='Feature'.) There are two Job Service workflows that manage this "state" of the features.

Call /transitionjobstate/{jobId}/{newState?} to transition the state of the job, and the state of all pending edit features whose current state matches the job state, to a specified new state. If no newState value is specified, then the request is treated as a query for the current job state and the states of the pending edits features in the job. This workflow assumes that the set of possible job states is at least a subset of the set of possible feature states.

Call /translatefeaturestate/{jobId}/{newState?} to transition the state of a specified set of features to either a default next state or a specified new state. If no newState value is specified, then the request is treated as a query for the current job state, default next state and possible other next states for the set of specified features.

Methods

Method Uri Description
GET /jobs?id={id}&owner={owner}&status={status}&description={description} Provides job attribute information for the jobs that match one or more filter parameters.
POST /job/{jobId?} Creates a new job with the specified job id, if specified. The job attributes are returned. These attributes can be edited and passed into the Edit API for updating.
POST /job/{jobId}/edit Update the specified job's attributes. The job attributes are in the post body.
POST /job/{jobId}/close Close the specified job if there are no pending edits.
GET /pendingedits/{jobIdList} Gets the list of pending edits for the specified jobs.
GET /conflicts/{jobIdList} Gets the list of conflicts between job edits and master deltas for the specified job.
GET /picklistvalues Returns the picklist values for the given attribute number.
GET /transitionjobstate/{jobId}/{newState?} Transition job to specified state or return information about current state of job.
POST /job/{jobId}/validate Validate the specified job's pending edits.
POST /job/{jobId}/post Post pending edits for the specified job.
POST /job/{jobId}/discard Discard pending edits for the specified job.
POST /job/{jobId}/discardbyfid Discard pending edits for the specified FIDs for the specified job. The FIDs are specified in the message body.
POST /translatefeaturestate/{jobId}/{newState?}[? useDefault={true or false} ] Translate specified features to the default next state or the specified next state based on their current state; or return a list of possible next states based on the current state of the features.
