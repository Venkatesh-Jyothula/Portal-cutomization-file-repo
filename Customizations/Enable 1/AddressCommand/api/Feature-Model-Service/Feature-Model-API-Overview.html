Feature Model API Overview

The HxGN NetWorks Feature Model Service is a standard OData v4.0 web service that exposes HxGN NetWorks Core data and metadata as a simple, hierarchical data model of features, components, attributes and relationships. Support for the OData protocol makes the Feature Model Service immediately accessible by clients (such as Microsoft Excel and Power BI) that understand OData data sources. This greatly simplifies the extract, transform and load steps when performing business analytics on the HxGN NetWorks Core data.

The HxGN NetWorks Core Web Services | Admin Console's Service Deployment module allows the administrator to easily define a feature model by selecting the features and components to include from a grid of all possible features and their components. After defining the model, the administrator deploys an instance of the Feature Model Service that can work with the model.

The model features have simple properties for the FNO and FID and have complex properties for the components of the feature. The components have properties for each of their attributes. Repeating components are collections of complex properties. The relationship types that the feature participates in are also modeled as collection properties of the feature (e.g. Owns, OwnedBy, ConnectsTo, ConnectsFrom, Contains, ContainedBy, Node1Connects, Node2Connects).

All of the workflows supported by the HxGN NetWorks Feature Model Service require a NetWorks_WFS license feature, except for the edit workflows, which require a NetWorks_WFST license feature.

Supported Feature Model Service Workflows

Querying feature data:

The Feature Model Service supports a workflow that is essentially a spatially restricted, ad-hoc query within a single feature class.

Clients use the $filter query parameter in the service call to fetch just the instances of the feature class that match the filter expression. The OData filter syntax supports logical, relational, arithmetic operators and a set of built-in functions that operator on numeric, string, date / time and collection data types.

The queries for feature data can be spatially restricted via an optional bounding box parameter. OData’s support for spatial operations was limited to point features, which was insufficient for HxGN NetWorks Core data. Hence, the Feature Model Service replaced those built-in functions with a new bounding box (BBox) query parameter that spatially restricts the search for all feature geometry types.

The queries for feature data can be further restricted to just the set features that are contained in a specified “FilterSet” parameter. The filter set can specify the result of a previous analytical operation (such as a trace or search from the Analytical Service) or from the pending feature edits in a job as follows:

FilterSet = Trace.

FilterSet = Search.

FilterSet = Job.

FilterSet = ..

FilterSet can be used in addition to OData $filter expression and the BBOX spatial restriction query parameter.

When the MeasureFeatures=true parameter is specified, then the linear and area type geometry components will be measured and returned in the response. If the BBOX parameter is specified then the percent of the feature that falls within the bounding box is also computed. For linear geometry feature components, there will be Length and Percent attributes added to the component. For area geometry components, there will be Area and Percent attributes added to the component.

By default, all measurements are done using the curved Earth model (i.e. using geographic reference space). If MeasureOnCurvedEarth=false is specified, then the measurement will use the projection reference space.

Client applications have full control over which feature properties are returned in the service response. There is also support for pagination of the response data via OData’s "$count=true", “$top=N”, “$skip=N” and "$orderBy={attribute}" query parameters.

Editing feature data:

The Feature Model Service provides a simple set of REST APIs for creating, updating and deleting HxGN NetWorks Core features.

Clients create a new feature by sending an HTTP POST body with a Json description of the feature. This can be as simple as a Json object with just a G3E_FNO property specified. If the client requests that some or all components be returned in the response, it will see the components with their default attribute values filled in plus any attribute values populated by functional interfaces associated with feature creation.

To update a feature, the client simply queries for the feature and requests that the components to be modified be returned in the response. Then the client updates the attributes and sends the feature and modified components back to the service with a HTTP PUT operation. To add a new repeating component to a feature, the client creates the Json for the component and omits the G3E_CID value or sets it to zero and includes the new component in a feature update operation.

Features are easily deleted by sending a HTTP DELETE message with the feature type and G3E_FID in the URL.

Querying feature metadata:

The Feature Model Service also provides easy access to feature metadata. There are two sets of API for metadata; one set returns metadata about the features, components, attributes and relationships for just the features in the published model, and the other set of APIs returns metadata on all HxGN NetWorks Core features, components, attributes and relationships.
